# 宠友邻产品与架构说明

## 1. 产品定位

宠友邻是一个同城宠物互助平台，连接两类用户：

- 宠物主人：需要代遛狗、上门喂养、家庭寄养、临时照护、接送或应急陪护。
- 兼职铲屎官：希望利用空闲时间承接附近宠物照护任务，积累服务记录和评价。

当前版本是 Web MVP，目标是完整演示“找服务 / 发单 / 接单 / 记录 / 社区 / 客服”的主要体验。

## 2. 当前用户体验原则

- 首页不区分登录状态：宠物主人登录、铲屎官登录、未登录时首页内容保持一致。
- 登录后通过导航和个人菜单体现身份差异。
- 宠物主人侧强调发布需求、管理订单和宠物档案。
- 铲屎官侧强调任务大厅、接单记录和服务表现。
- 客服作为全局能力存在，不被具体页面重写。

## 3. 当前核心闭环

### 3.1 宠物主人闭环

1. 打开首页查看服务介绍与附近任务预览。
2. 登录或注册为宠物主人。
3. 进入“找服务”查看服务发布入口和附近铲屎官。
4. 进入“发单大厅”填写订单：服务类型、时间、宠物、疫苗、地址、宠物性格。
5. 订单进入待支付，支付后进入待接单。
6. 进入“我的订单”查看状态，支持支付、取消、确认完成、申诉、退款。
7. 进入个人中心查看账户、宠物档案和常用工具。

### 3.2 铲屎官闭环

1. 登录或切换为兼职铲屎官。
2. 顶部导航“找服务”显示为“任务大厅”。
3. 进入任务大厅，按服务类型、距离、时间、报酬筛选任务。
4. 查看任务详情：订单摘要、服务时间、地址、宠物详情、主人的嘱咐和主人认证信息。
5. 点击在线沟通或立即抢单。
6. 顶部导航“我的订单”显示为“接单记录”。
7. 进入接单记录，查看收入统计、完成单量、待服务/进行中/已完成/已取消任务。
8. 在个人中心查看服务表现、身份资料、工作台和最近评价。

### 3.3 社区与客服闭环

- 社区用于发布宠物动态、浏览图文瀑布流和话题内容。
- 用户可删除自己发布的动态。
- 右下角在线客服浮窗支持登录用户历史会话和未登录临时会话。

## 4. 前端页面地图

| 路由 | 页面 | 当前说明 |
| --- | --- | --- |
| `/` | 首页 | 登录/未登录内容一致，展示品牌、服务、保障、附近任务预览、社区精选 |

## 5. 功能模块说明

### 5.1 首页

当前首页统一展示：

- Hero 视觉与品牌文案
- 立即预约服务、成为铲屎官入口
- 搜索框和附近推荐
- 服务类目
- 平台保障
- 附近待接任务预览
- 地图视图演示
- 社区精选

登录后按钮点击仍会进入对应业务路径，但页面展示不再因身份切换。

### 5.2 认证与身份

- 手机号登录使用验证码演示流程。
- 微信登录使用模拟扫码流程。
- 登录时可选择宠物主人或铲屎官。
- 顶部头像菜单支持切换身份。
- 身份切换会影响导航文案和部分页面内容。

### 5.3 宠物主人能力

- 找服务页面：发布需求表单、服务类型、预算、服务地址、宠物选择、备注、附近铲屎官列表。
- 发单大厅：完整订单表单、半小时粒度时间约束、自动计价、地图取点。
- 我的订单：分状态筛选、搜索、支付倒计时、取消、确认、申诉、退款。
- 个人中心：账户信息、宠物档案、工具入口、邀请卡片。

### 5.4 铲屎官能力

- 任务大厅：左侧筛选、中间任务列表、右侧任务详情。
- 任务详情：顶部图片、订单摘要、主人的嘱咐、主人认证卡、在线沟通、立即抢单。
- 接单记录：状态 tabs、月收入、完成单量、服务卡片、打卡/准备出发/导航入口。
- 个人中心：核心表现、身份资料、工作台、最近评价。

### 5.5 社区

- 支持发布文本、标签和图片。
- 支持话题选择和自定义标签。
- 使用瀑布流展示内容。
- 仅作者本人可删除自己的帖子。

### 5.6 在线客服

- 全局悬浮入口，不依赖具体页面。
- 登录用户使用账号会话。
- 未登录用户可创建临时会话，关闭后前端不保留临时聊天。
- 后端会自动生成客服回复。

## 6. 当前后端能力

后端已提供真实 API 路由，默认数据来自内存 Mock Store。主要能力：

- 登录与角色切换
- 用户信息与位置
- 宠物列表与新增宠物
- 首页聚合数据
- 订单创建、支付、接单、开始服务、完成服务、确认评价、申诉、退款、取消
- 附近订单查询
- 社区帖子增删查
- 客服临时会话和消息

## 7. 数据与存储策略

当前采用“双轨”策略：

- 演示主流程：Mock Store 内存数据，启动后即可体验。
- 数据库基础设施：PostgreSQL + PostGIS + Redis 已提供，但尚未全面接入业务。

部分宠物新增逻辑会尝试写入 PostgreSQL，用于验证持久化通道。后续正式化时建议把所有 Store 操作替换为 Repository。

## 8. 当前架构

```text
浏览器
  ↓
Vue 3 前端
  ↓ client.ts
FastAPI /api/v1
  ↓
MockStore（当前主要数据源）
  ↓ 可选
PostgreSQL + PostGIS / Redis
```

前端 `client.ts` 在后端不可用或部分请求失败时会降级到 `frontend/src/api/mock.ts`，保证演示可继续。

## 9. 当前演示边界

- 短信验证码和微信登录是演示逻辑。
- 支付、退款、申诉是状态流转演示，不接真实资金。
- 任务大厅和接单记录中的部分展示数据为前端静态演示数据。
- 订单真实持久化尚未全面接入 PostgreSQL。
- Redis 未接入订单锁、通知或缓存。
- OSS 文件上传和内容审核未接入。

## 10. 下一阶段建议

1. 接入真实数据库 Repository，替换 Mock Store。
2. 补齐订单状态机和并发锁，防止重复接单。
3. 接入正式短信、微信、JWT/Session 鉴权。
4. 支付、退款、申诉和违约金进入真实流程。
5. 客服会话和消息持久化。
6. 社区媒体上传迁移到 OSS。
7. 铲屎官认证、排期、收入结算和评价体系落库。
